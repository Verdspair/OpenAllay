# OpenAllay 0.2 Platform Iteration Design

**Date:** 2026-07-25  
**Status:** Accepted for implementation  
**Decision:** SKMB-2026-07-25-029  
**Release line:** 0.2.x

## Objective

Turn the working 0.2 JavaScript Agent into a coherent Minecraft Agent platform:
make core capabilities immediately usable, reserve Skills for vertical
knowledge, establish installable Skill and Extension communities, finish
server-model discovery, add focused world observation, and measure progress
with a reusable benchmark rather than manual impressions.

## Architecture choice

Three approaches were considered:

1. Continue adding first-party features directly to OpenAllay. This is quick
   but grows a monolith and keeps model guidance, mod adapters, and UI coupled.
2. Build one capability kernel with two package ecosystems. Core JS literacy is
   always present; Skills teach vertical workflows; Extensions add Java-backed
   typed capabilities. This is selected.
3. Add a general dynamic plugin or external scripting runtime. This is flexible
   but creates a second orchestration/permission system and conflicts with the
   in-JVM loader architecture.

The selected system has one model-facing analysis Tool and one progressive
Skill Tool:

```text
Minecraft/mod APIs on owning thread
  -> immutable detached snapshots
  -> OpenAllay Extension SPI
  -> declared HostSchema + JavaScript host graph
  -> run_javascript
  -> canonical JSON + trusted semantic sidecar
  -> compact model result + native player UI

Agent Skills package
  -> validated metadata/instructions/references
  -> load_skill only for a matching vertical workflow
```

## Core prompt and Skill boundary

`AgentSystemPrompt` receives a generated `CoreJavascriptContract`. It lists the
complete stable top-level surface and compact declared schemas for `mc`,
`schema`, `workspace`, `helpers`, `require`, and optional request bindings. The
contract is generated from the same `HostRootDescriptor` catalog used by Rhino,
so documentation cannot drift from runtime mounting.

The prompt teaches:

- direct path access and host-view immutability;
- one-program collection analysis;
- focused dynamic-field discovery;
- bundled module loading;
- typed result behavior and workspace continuation;
- optional capability discovery.

It does not mandate `analyze-game-data`. That Skill is removed as a generic
preflight because its content is core literacy. Existing broad Skills are
audited: universal instructions move into the core contract; genuinely
vertical content remains; redundant broad fallback Skills are removed.

`load_skill` remains progressive. A request ledger distinguishes continuation,
first complete load, rehydration after compaction, and an actual duplicate.
Repeated complete loads return a compact `already_loaded` receipt instead of
duplicating the document in context. Prompt wording says “load a matching
vertical Skill once” rather than making every non-trivial call a preflight.

## Skill community

The public `OpenAllay-Skills` repository contains:

- `catalog.json` schema 2;
- one directory per Skill;
- package metadata, compatibility, version, archive URL, SHA-256, and source;
- CI that validates Agent Skills subset rules, references, archives, and
  deterministic catalog ordering.

The game caches the catalog under `config/openallay/catalogs/skills.json`.
Settings provides installed and community tabs, search, refresh, install,
update, local directory/ZIP import, source/provenance, validation diagnostics,
and read-only preview/edit entry points. Installed Skill files remain ordinary
external Markdown packages and can be edited by the managed Skill API.

Remote download and local import converge on `SkillPackageInstaller`. It stages,
normalizes, parses, validates, then atomically publishes. Catalog failure is
non-destructive and does not affect Agent requests.

## Extension platform and community

`OpenAllayExtension` is a common SPI discovered through loader-owned
registration. The SPI contributes immutable declarations:

- identity and compatibility;
- `JavascriptDataModule` factories;
- bundled JS modules;
- bundled Skills;
- typed result presentation adapters.

Loader adapters pass only registered declarations into common code. Capturing
live data remains a separate owning-thread hook that must return detached
closed host values.

The public `OpenAllay-Extensions` repository contains catalog metadata and
release artifacts for normal Fabric/NeoForge Extension JARs. In-game install or
local JAR import stages a compatible artifact and clearly requires restart.
Every distributable JAR embeds `META-INF/openallay-extension.json`. Local
import obtains identity and compatibility from this strict manifest and does
not require the package to already appear in the community catalog. Catalog
schema 2 groups the separate Fabric and NeoForge JARs for one logical Extension
version under loader-specific artifact records. Installation resolves the
current loader before HTTP, then binds the embedded manifest to that artifact's
checksum and mod metadata. OpenAllay does not attempt unsupported hot class
loading.

Settings becomes a real Extensions master-detail page:

- installed/active/pending/incompatible/community filters;
- Extension summary, provider, version, loader, game/API compatibility;
- contributed roots, schemas, JS modules, Skills, and native views;
- diagnostic and source information;
- community refresh/install/update/local import;
- experimental capability controls in their own section.

The first-party JEI and REI adapters graduate from recipe-only bridges into
Extensions. Their recipe providers remain the factual source, while the
Extension projection adds structured provider/category/focus/navigation
metadata to JS. A third content-rich integration is selected only after
verifying a public 26.2 API; Patchouli/FTB Quests remain knowledge adapters
rather than being relabeled merely to increase the count.

## Server model completion

The existing common server runtime remains authoritative. The repair focuses on
bootstrap diagnostics and client projection:

- load only `config/openallay/server-model.json` plus documented environment
  overrides;
- report exact redacted validation state server-side;
- construct the runtime before initial capability advertisement;
- advertise canonical model ID and budget whenever valid;
- update capability on lifecycle changes;
- project a read-only “Server” choice in the same Models page and conversation
  selector, visually distinct from editable local profiles;
- never show client edit/test/delete actions for it.

Both loaders share capability payload semantics and receive parity tests. A
dedicated-server fixture proves that a configured model appears automatically
after join and disappears on disconnect.

## Stable commands

Commands remain experimental and default-off. The existing complete Brigadier
catalog and exact player submission design stays intact. The stabilization
slice focuses on:

- one Skill load per command workflow;
- deterministic feedback correlation/quiet-window tests;
- no-feedback and rejection presentation;
- cancellation before submission versus non-rollback after submission;
- mod-registered command fixtures;
- modern item-component examples that teach the general command grammar
  without embedding one benchmark answer.

## Focused world observation

World observation is a separate optional `world` binding selected in
`run_javascript.roots`. It is read-only and does not depend on command mode.

```javascript
const slice = world.inspect(
  {from: {x: 0, y: 64, z: 0}, to: {x: 31, y: 64, z: 31}},
  {includeAir: false}
);
return slice.blocks.filter(block => block.id.includes("_log"));
```

Block results include absolute and relative coordinates, stable ID, state
properties, loaded coverage, evidence, and completeness. Entity discovery
returns summaries and opaque request-scoped IDs; `world.entity(id)` returns one
deeper detached snapshot.

Capture is not performed on the Rhino worker. A common observation coordinator
marshals resumable capture slices to the owning client/server thread and
completes a future consumed synchronously by the isolated Rhino scope. Only
loaded/visible state is represented. The server route can provide authoritative
data for a requesting player; the client route reports client-visible
authority. Results use the normal workspace so large observations can be
filtered again without feeding raw matrices to the model.

## Benchmark

`benchmarks/` contains corpus manifests and fixture documentation. The common
runner consumes the same `GameGuideAgent`, trace model, Tool definitions, and
result normalizer as production.

Initial suites:

- core exact lookup without Skill;
- collection ranking and aggregation in one JS call;
- dynamic Extension schema discovery;
- recipe cost/craftability;
- installed-mod and settings lookup;
- experimental command discovery and execution;
- modern item-component command construction;
- server-model selection/routing;
- JEI/REI Extension data;
- block cross-section and entity inspection.

Each case has machine-verifiable predicates outside model context. Live runs
support an explicit repeat count and report:

- successful attempts / total attempts;
- median and distribution of model turns;
- Tool calls and `run_javascript` calls;
- first-load, continuation, rehydration, and duplicate Skill loads;
- invalid calls, corrected calls, and terminal failure categories.

Read-query cases verify the final answer rather than searching the complete
Tool-result envelope. A correct intermediate lookup does not count as task
completion when the Agent omits or contradicts it in the final answer.

Time is retained only as diagnostics. Reports compare corpus version, product
commit, model identity, and provider without interpreting network latency as
Agent quality.

## Delivery slices

1. Core prompt and Skill lifecycle.
2. Skill catalog/repository and in-game installation.
3. Extension SPI, settings, catalog, JEI/REI adapters.
4. Server-model bootstrap and read-only model UI.
5. Command stabilization and world observation.
6. Benchmark runner, expanded mod profile, and iterative fixes.
7. Verified 0.2.x patch releases at coherent player-useful checkpoints.

Each slice keeps Fabric and NeoForge parity and must leave the prior installed
catalog/package/runtime generation usable on failure.
