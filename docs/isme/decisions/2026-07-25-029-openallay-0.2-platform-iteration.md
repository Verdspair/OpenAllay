## Decision

### Core prompt and Skills

The stable `mc`, `schema`, `workspace`, `helpers`, `require`, and
`run_javascript` contract is core Agent literacy. A compact descriptor-derived
schema and tested syntax guide are included in every client- and server-model
system prompt. Simple and analytical use of those core capabilities does not
require a Skill preflight.

Skills contain vertical domain knowledge or an optional workflow that is not
universally relevant. The experimental command capability retains its matching
Skill. Mod-specific mechanics, guide conventions, progression strategies, and
Extension-specific workflows may also use Skills.

A request-scoped Skill ledger identifies documents by package, document path,
and content fingerprint. A completed document already retained in the active
request is not loaded again. Progressive continuation of an incomplete
document is not a duplicate. Context compaction retains a compact loaded-Skill
receipt; when instructions are intentionally omitted by compaction, a later
reload is allowed and recorded as a rehydration rather than a duplicate.

### Community package catalogs

OpenAllay uses separate public catalogs for Skills and Extensions. Catalog
manifests are versioned, deterministic JSON documents, while package contents
retain their native formats.

Skill packages are Agent Skills-compatible directories or ZIP archives with a
root `SKILL.md` and declared references. A candidate is extracted into a
private staging directory, path-normalized, parsed, dependency-checked, and
atomically published into `config/openallay/skills/<name>/`. The prior valid
package remains active until publication succeeds. Local directory/ZIP import
uses the same validation path as a catalog download.

Community packages carry their package version in the namespaced
`metadata.openallay/version` string. The catalog version is the available
version; the installed document metadata is the durable installed version.
An older package without this metadata has unknown version and is offered one
tracked update rather than being silently treated as current. A successful
update publishes the catalog version with the package, after which an equal
version is current and a different version is updateable.

The Skill community catalog uses strict schema 2. Each package supplies a
player-facing display name, concise description, and publisher in addition to
its stable machine ID, version, archive, checksum, compatibility, and source.
These catalog fields describe the package before installation; the validated
package's root `SKILL.md` remains the authority for Agent instructions after
installation. OpenAllay has not formally shipped a Skill catalog cache, so
development-era schema-1 caches are not migrated or accepted. Catalog
publication, cache decoding, and codec output all require schema 2. Unknown
versions and unknown fields fail closed.

An Extension is a normal Fabric/NeoForge mod JAR implementing the OpenAllay
Extension SPI. It embeds a strict schema-1 package manifest at
`META-INF/openallay-extension.json`; this manifest is the identity and
compatibility authority for local import. The community catalog uses schema 2:
one logical Extension ID/version groups one independently verified artifact
URL, SHA-256, and mod-ID set per supported loader. The current loader is
selected before download or staging. It cannot be
safely hot-loaded into a running Minecraft class loader. Catalog download and
local import therefore validate the embedded identity, loader, Minecraft
range, OpenAllay API range, actual SHA-256, and mod metadata, then stage the
JAR for the next restart. Catalog download also requires its descriptor,
mod IDs, and checksum to match the embedded package. The UI reports
`restart_required`; it never claims the code is active before the loader
registers it. The initial catalog does not require a signature authority, but
integrity and provenance remain visible and no unverified checksum is treated
as verified.

Catalog refresh is asynchronous configuration-layer HTTP. A successful
generation atomically replaces its cache. Network, decoding, or package failure
retains the prior valid cache and every installed package. Catalog I/O is not
an Agent Tool and is never placed in model context.

Opening a Skill or Extension community tab starts at most one automatic
refresh for that settings-screen lifetime. A cached generation stays visible
while the request runs. A failed automatic refresh remains visible as a
diagnostic and is not retried in a loop; the player may explicitly retry.

### Extension runtime

OpenAllay publishes a small common Java SPI. An Extension registers:

- descriptor metadata and compatible loader/game/API ranges;
- detached JavaScript data modules with declared closed host schemas;
- optional bundled JavaScript modules;
- optional Agent Skills;
- optional typed result presenters whose factual input remains canonical JSON.

Registration occurs during loader initialization. Duplicate IDs fail only the
new Extension registration and produce a visible diagnostic. Capturing one
Extension failure degrades that Extension without removing core roots or other
Extensions. Live Minecraft or mod objects are captured only on their owning
thread and detached before Rhino execution.

JEI and REI become first-party Extensions over their verified public APIs and
existing OpenAllay recipe bridges. Their structured JS values expose provider
availability, categories, recipes, focus/navigation support, and diagnostics
without leaking their live runtimes to worker threads. Additional content-mod
adapters follow the same SPI rather than adding model Tools.

### Server models

A server model is configured only by
`config/openallay/server-model.json` or server process environment. On
connection, a valid server runtime advertises a stable connection-scoped
descriptor containing canonical model ID and context budget. The client
automatically registers that descriptor as a read-only model choice with a
server badge. It cannot edit, test, delete, or persist the server configuration.

Invalid or absent server configuration advertises no server model and exposes
a server-local diagnostic. Capability changes replace only future-request
selection state. Disconnect removes the choice and converts a selected server
model back to the local default without leaking it to another connection.

### World observation

Spatial observation is a core optional JavaScript binding named `world`. The
request captures only the authority and connection needed to make later
observations; it does not eagerly copy the world.

`world.inspect(bounds, options)` captures every loaded block position in the
inclusive cuboid, including stable block ID, relative/absolute position, and
detached block-state properties. It returns explicit loaded coverage and
missing/unavailable regions. Capturing runs on the owning client/server thread
in resumable slices, while Rhino waits only on its worker thread. Cancellation
stops uncaptured slices and publishes no fabricated complete matrix.

`world.entities(bounds, options)` returns a detached entity summary with a
request-scoped opaque observation ID. `world.entity(id)` deepens one entity
from the same request snapshot. IDs cannot be constructed to inspect another
request or player. World observation is read-only and distinct from the
experimental command capability.

No arbitrary project volume, entity-count, or result-row cap is introduced.
The caller is taught to choose a task-focused cuboid or cross-section.
Model-facing result projection remains bounded by the existing total output
budget and preserves a workspace handle for further JavaScript filtering.

### Benchmark

The benchmark corpus is versioned data rather than hard-coded answers in a
prompt or Skill. Each case declares:

- player request and required fixture capabilities;
- deterministic setup/fixture identity;
- machine-verifiable outcome predicates over canonical results, final evidence,
  or observed command/world effects;
- maximum semantic expectations only when the product already defines one.

Runs record attempt count, success/failure, model turns, Tool calls, JavaScript
executions, Skill loads/reloads, invalid calls, and correction calls. Wall-clock
latency is diagnostic only and is excluded from comparative scoring.
Repeated live-provider attempts report completion probability and distribution
of Tool rounds. Deterministic replay remains offline and live-provider runs
remain explicit opt-in operations.

Each retained attempt has one typed primary failure stage. A failed Agent
terminal state takes precedence over result-verification failure, which takes
precedence over the model-turn budget. The terminal code or verifier diagnostic
is retained with that attempt. These stages are observable facts; the runner
does not guess whether the root cause belongs to prompt, Skill, schema,
Extension, command, world, provider, or fixture. That domain classification is
made from the retained trace during the post-run audit.

Read-query and analysis cases verify the final answer field. Tool results remain
retained evidence for diagnosis, but merely retrieving a target value does not
prove that the Agent completed the player request. Command cases continue to
verify independently observed effects.

The retained live-report schema is 4 after adding typed attempt records, and
the stricter answer-verification corpus is `openallay-core-2026-07-25-r2`.
Earlier development reports are not migrated or compared as the same scoring
generation.

The corpus includes lookup, schema discovery, whole-collection analysis,
recipes/craftability, optional commands, server-model routing, Extension data,
and world observation. “Create an upgraded sword” verifies generic command and
component reasoning against fixture state; no exact sword command is embedded
in the system prompt or a Skill. Server-model routing uses a dedicated
GuideService fixture because connection-scoped endpoint selection is not a
JavaScript Agent capability. Benchmark selection reports fixture mismatch
separately from missing fixture capabilities and explicit unavailable
selections fail rather than silently shrinking the run.

### Release cadence

This program remains the OpenAllay 0.2 line. Coherent, player-useful,
verified increments may ship as 0.2.1, 0.2.2, and later patch versions. The
program does not create a 0.3.0 release.

## States

- `catalog_cache_ready`: one validated catalog generation is readable.
- `catalog_refreshing`: a background catalog request is in flight while the
  prior valid generation remains readable.
- `package_staging`: one downloaded/imported package is isolated and being
  validated.
- `skill_published`: a validated Skill package atomically owns its local path.
- `extension_restart_required`: a validated Extension JAR is staged but is not
  active until the next compatible loader restart.
- `extension_registered`: loader startup accepted one Extension descriptor and
  its contributions.
- `server_model_advertised`: the current connection exposes one valid read-only
  server model descriptor.
- `world_capture_wait`: Rhino is waiting for an owning-thread spatial capture.
- `world_snapshot_ready`: one request-scoped detached observation is available.
- `benchmark_running`: one corpus attempt owns isolated trace and metric state.

## Transitions

1. `catalog_cache_ready -> catalog_refreshing`: start one asynchronous refresh
   from the first community-tab visit or an explicit retry, and keep the prior
   generation readable.
2. `catalog_refreshing -> catalog_cache_ready`: atomically publish a valid
   manifest or retain the prior generation with a redacted diagnostic.
3. `catalog_cache_ready -> package_staging`: download one catalog-selected
   package, or import one local package selected by its embedded manifest.
4. `package_staging -> skill_published`: validate and atomically replace one
   Skill package.
5. `package_staging -> extension_restart_required`: validate and stage one
   Extension JAR for loader restart.
6. `extension_restart_required -> extension_registered`: compatible loader
   startup registers the Extension SPI contribution.
7. `connection capability received -> server_model_advertised`: install or
   replace the current read-only server choice for future requests.
8. `server_model_advertised -> absent`: disconnect or capability withdrawal
   removes the choice and selects the local default for future requests.
9. `javascript_executing -> world_capture_wait`: validate bounds and marshal
   capture to the owning game thread.
10. `world_capture_wait -> world_snapshot_ready`: detach captured blocks or
    entities, publish coverage/evidence, and return to Rhino.
11. `world_capture_wait -> cancelled/failed`: stop remaining slices and return
    a structured observation failure.
12. `idle -> benchmark_running -> completed/failed`: run one isolated corpus
    attempt and retain canonical metrics.
13. `skill_published with unknown/older version -> package_staging ->
    skill_published with catalog version`: explicitly update one package;
    validation/publication failure retains the prior package and version.

## Invariants

1. Core JS literacy is present without loading `analyze-game-data`.
2. A completed unchanged Skill is not redundantly loaded in one retained
   request context.
3. Skill packages cannot register code, Tools, network access, or permissions.
4. Extension code is active only after the Minecraft loader loads a compatible
   JAR; UI staging never implies activation.
5. Catalog refresh and package failure never destroy a prior valid catalog or
   installed package.
6. Extension IDs and contributions have one owner; one Extension failure does
   not remove unrelated capabilities.
7. Client settings never mutate server-model configuration.
8. Server-model identity and availability never survive their connection.
9. Live world, registry, entity, and mod objects never enter a Rhino worker.
10. Every spatial result states authority, coverage, completeness, capture
    time, and provenance.
11. World observation is read-only; command mutation remains separately gated.
12. Benchmark scoring uses external predicates and canonical traces, never
    fixture answers injected into Agent guidance.
13. The release line remains 0.2.x until a later explicit designer decision.
14. Community Skill update state compares the catalog version with durable
    namespaced package metadata; missing metadata is unknown, never proof that
    an installed package is current.
15. Skill catalog display metadata never replaces the installed package's
    validated `SKILL.md` as the Agent-instruction authority.

## Failure Semantics

- Catalog transport/decoding failure: retain prior cache and report
  `catalog_refresh_failed`.
- Unsupported Skill catalog schema, including development-era schema 1:
  reject the generation, retain no invalid replacement, and report
  `catalog_refresh_failed`.
- Skill package validation/publication failure: retain the prior package and
  report `skill_install_failed`.
- Extension checksum/compatibility/metadata failure: activate nothing and
  report `extension_install_failed`.
- Duplicate or invalid Extension contribution: reject only that Extension and
  report `extension_registration_failed`.
- Missing/invalid server config: advertise no model and report the failure only
  in server diagnostics.
- Withdrawn server capability: reject new server selection, select the local
  default for future requests, and never reroute an already active request.
- Unloaded/out-of-view world region: return partial coverage, not empty proof.
- Disconnect/cancel during capture: fail `world_observation_cancelled`, discard
  incomplete detached values, and suppress late slices.
- Benchmark provider instability: retain the failed attempt and continue only
  according to the runner's explicit requested attempt count.
- Benchmark attempt failure: retain one typed primary stage and diagnostic;
  never relabel an Agent terminal failure as a model-turn budget failure.
